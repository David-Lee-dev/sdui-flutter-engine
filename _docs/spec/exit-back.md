# Exit back lifecycle (0.28.0)

User decision 2026-11-13: the engine only *detects* an Android system back that would close the app and exposes it to templates as a lifecycle moment. What happens next (open a bottom-sheet modal, exit, ...) is template behavior built from existing commands. The engine does not open modals or decide UX. This replaces the earlier unpublished 0.28.0 design with an app callback (`Sdui.router(onExitBack:)`, `SduiExitBackHandler`), which has no consumers and is removed. The router mechanism stays: a `GoRouter` subclass (via `GoRouter.routingConfig`) whose only override is `backButtonDispatcher`, an exit-aware `RootBackButtonDispatcher` (structure approved 2026-11-13).

## Requirements
- X1 `_scope._lifecycle` accepts `on: exit_back` (with `action`; `delay`/`every` follow the existing per-trigger rules: `every` rejected, `delay` not meaningful — reject or ignore consistently with `remount`/`dispose`). A template using it must declare the new feature `lifecycle_exit_back_v1` in root `_requires`, enforced like `anchored_overlay_v1` (compile error naming the feature when missing).
- X2 `Sdui.router` always installs the exit-aware dispatcher. It first runs the normal `RootBackButtonDispatcher` flow (child dispatchers, router delegate: nested/root navigators, `PopScope`, go_router `onExit`). If that handles the back, no hook runs.
- X3 When the normal flow leaves the back unhandled, the dispatcher fires the `exit_back` hooks of every currently visible scope that declares one and returns `true` (back consumed, app stays). If no visible scope declares one, it returns `false` and Flutter closes the app exactly as before.
- X4 "Visible" uses the same notion as the `remount` trigger (current route and enabled `TickerMode`, covering inactive shell branches and outer navigators). A scope is a candidate only while mounted, visible and not exiting (presence); disposal or becoming obscured removes it.
- X5 Hooks fire through the scope's own action host like other lifecycle hooks, with a new action origin `exit_back`. Repeated exit backs while the action's foreground flow is still running are deduplicated by the existing action `_dedupe` (default true); the back is still consumed.
- X6 `exit_back` is never scheduled by mount/render/interval/remount/dispose processing.
- X7 Remove `onExitBack` from `Sdui.router` and the `SduiExitBackHandler` export.
- X8 Layering: the visible-hook registry lives in `lib/src/runtime/`; the dispatcher in `lib/src/shell/` reads it. `test/architecture_boundary_test.dart` stays green; `compile`/`ir` stay Flutter-free.
- X9 Docs: `docs/lifecycle.md` lists `exit_back`; `docs/exit-back.md` describes the template usage and the Android 13+ precondition (the host app must keep `SystemNavigator.setFrameworkHandlesBack(true)`, otherwise the OS closes the app without Flutter seeing the back; the engine does not set it) and that exiting after a confirmation needs an app-provided command (e.g. an external `sys_exit_app`). CHANGELOG `## 0.28.0` describes this design (not the removed callback); pubspec stays 0.28.0. Do not publish.

## Tests
Through public mounts (`Sdui.router` + `MaterialApp.router`, `EngineRunner`/`SduiScreenPage` with templates, `WidgetsBinding.handlePopRoute()`, `SystemNavigator.pop` observed on `SystemChannels.platform`): compiler accepts `exit_back` with the feature and rejects it without; unhandled back with a visible hook fires it once and does not exit; no hook exits; pushed route / `PopScope(canPop:false)` / go_router `onExit` veto handle the back without firing; a hook on an inactive shell branch or an obscured screen does not fire; a hook whose action is still running is deduplicated on a second back and the app still stays; a disposed scope no longer counts.
